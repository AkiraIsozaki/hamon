# コード設計の規律

仙塲大也『良いコード/悪いコードで学ぶ設計入門』の語彙（悪魔、完全コンストラクタ、目的駆動名前設計など）で書く。各規則の出典は人間向けに `SOURCES.md` にあり、作業時に読む必要はない。

規則は言語を問わない。書く言語に同じ目的の仕組み（不変の宣言、可視性、型注釈、列挙型など）があればそれを使い、無ければ慣習と検証で同じ状態を保つ。

**規約の正はこのファイルであり、既存コードではない**。既存コードがここに反していたら、それは手本ではなく直す対象。触るファイルで違反を見つけたら、機能変更とは別のコミットで直す。

隣接するスキルとの分担:

- `mattpocock-skills:codebase-design` は**モジュールと境界**（深いモジュール、seam、アダプタ）。このスキルは**その内側のクラスと関数**。
- `ponytail:ponytail` は**書かない判断**（YAGNI、標準ライブラリ優先）。このスキルは**書くと決めたものの形**。両者がぶつかるのは「概念に型を与えるか」の一点で、次の節で解く。

## 型を与える基準（ponytail との境界）

「概念をクラスにするか、素の数値・文字列・辞書のまま渡すか」を判断する。値の渡し間違いはクラスで防ぎたいが、先回りのクラスは ponytail が禁じる。概念が**今のコードで次のどれかを満たすとき**にクラスを与える。

- 不変条件がある（割合は 0 以上 1 以下）
- 同じ基底型の別概念と取り違えうる（金額と数量はどちらも数値）
- その値に対する計算や判定がある（金額からグラフ上の y 座標を求める）

どれも満たさず、受け取って渡すだけの値はプリミティブや辞書のままでよい。

型を与えると決めたら、まず標準ライブラリを探す（日時型、十進数型、列挙型、順序付きの辞書）。無ければクラスにして、コンストラクタで検証し、生成後は変更できなくする。

将来の柔軟性のためのクラスや抽象は作らない。分岐が 1 箇所なら条件分岐でよく、同じ分岐が 2 箇所目に現れたときに型へ寄せる。

## カプセル化: データとロジックをひとつにまとめる

| 悪魔 | あるべき形 |
|---|---|
| **データクラス**: データだけ持ち、検証も計算もよそにある。重複・修正漏れ・不正値の元 | データを持つ型に、そのデータを使う計算と判定を置く。避けるのは「振る舞いを持たない入れ物」という設計。入出力の境界（外部データの読み込み）でだけ素のデータ構造を許す |
| **生焼けオブジェクト**と**不正値の混入** | **完全コンストラクタ**。コンストラクタで検証して例外を投げ、生成できたインスタンスは常に正しい。生成後の変更を封じる |
| **初期化ロジックの分散** | 目的別の名前を持つファクトリ（`Money.fromJson(...)` のような static / クラスメソッド）。ファクトリからも必ずコンストラクタを通す |
| **static メソッドの誤用** | 自分で定義した型のデータを引数に取って計算するだけの関数は、その型のメンバに移す。メンバでない関数は、自分で変更できない型（標準ライブラリ、外部ライブラリ）への操作と、ファクトリ・ログ・形式変換に使う |
| **インスタンス変数を使わないメソッド** | メンバ関数は必ず自身のプロパティを使う。使っていないなら置き場所が違う |
| **共通処理クラス** | `utils` / `helpers` / `common` を作らない。ロジックはそれが扱うデータの型へ。ログや例外処理のような横断的関心事だけは共通の置き場を持ってよい |
| **出力引数** | 引数で受けた可変オブジェクトを書き換えて結果を返さない。結果は戻り値 |
| **多すぎる引数** | 意味のある単位で型にまとめる。引数が増えるのはプリミティブ型執着の兆候。位置引数が 3 つを超えたら、名前付き引数（キーワード引数やオブジェクト引数）にする |
| **アクセス連鎖** | `a.b.c.value` と掘って判断しない。**尋ねるな、命じろ**: 状態を取り出して外で判断する代わりに、判断ごと相手に頼む |
| **現実の営みにない操作** | 型には意味のある操作だけを公開する。金額同士の乗算、ID の加算は定義しない。素の数値のまま使うとこれらが全部できてしまう |

## 不変

- **既定は不変**。変数は一度だけ代入する。言語に再代入できない宣言があればそれを既定にし、可変にするのは関数内に閉じた蓄積と、性能上の理由が計測で示された箇所だけ。
- **再代入しない**。同じ変数に別の意味の値を入れ直さず、目的ごとに変数を用意する。
- **変更は新しいインスタンスを返す**。既存の値を書き換えず、変更後の値を持つ新しいインスタンスを、目的の名前を持つメンバ関数で作る。
- 可変インスタンスを使い回さない、受け取った引数を変更しない。関数の影響範囲は引数と戻り値に限定する。並べ替え・追加・削除は自分が作ったコレクションにだけ行い、受け取ったコレクションからは新しいコレクションを作る。
- 値オブジェクトは生成後に変更できなくする（凍結、読み取り専用プロパティ、不変のデータクラスなど言語の仕組みで）。コレクションを保持するときは複製してから不変にする。
- 状態を持つ必要がある場合（画面やセッションの状態）は、可変の本体を非公開にし、読み取りは関数経由にする。
- **コード外とのやりとりは局所化する**。ネットワーク、ファイル、画面、環境変数、現在時刻、乱数への入出力は薄いアダプタに集め、ドメインの型と計算は入出力を持たない。

## 関心の分離

- **単一責任とは単一目的**。クラスの目的を 1 文で言う。「〜と〜」になったら分ける。
- **プロパティごとに分けられないか見る**。メンバ関数群が別々のプロパティだけを使っているなら、別々のクラスである。
- **DRY は概念の重複にだけ適用する**。形が同じでも目的が違うコード（入力値の上限チェックと表示件数の上限チェック）は共通化しない。
- **継承より委譲**。実装の継承はしない。振る舞いの取り換えは、同じ形のオブジェクトか関数を渡すことで行う。
- **なんでも公開しない**。モジュールやクラスから公開するのは外から使わせると決めたものだけ。それ以外は言語の可視性の仕組み（非公開の宣言や命名規約）で隠す。
- **非公開関数だらけ**は責務過多の兆候。非公開関数が扱っている概念を型として取り出す。
- **スマート UI**。画面やレポートなどの出力を作る関数は、計算済みの表示用の値を受け取って出力を組み立てるだけにする。判定・整形・計算は表示用の値を作る側（ドメインの型）に置く。出力を作る関数の中に `if balance < 0` のような業務判定を書かない。
- **トランザクションスクリプト**と**神クラス**。エントリポイント（`main`、リクエストハンドラ、CLI のコマンド）がなりやすい。エントリポイントは読み込み → ドメインの型に計算を頼む → 出力に渡す、の配線だけにし、規則そのものはドメインの型が持つ。
- **巨大データクラス**。何十ものプロパティを持つ型は、場面ごとの目的（一覧の 1 行、詳細画面、グラフ）で分ける。
- **グローバル変数**。モジュールのトップレベルやグローバルな名前空間に可変状態を置かない。
- **技術駆動パッケージング**。ファイルとディレクトリは `models/` / `utils/` / `helpers/` のような技術の種類ではなく、関心事で切る。関心事の名前は `CONTEXT.md` の語から取り、名前設計の規則（意味が狭いこと）をファイル名にも適用する。境界をどこに置くかは `mattpocock-skills:codebase-design` に従う。

## 条件分岐

- **早期 return**。前提を満たさない場合を先に返し、`else` を書かずに本筋をネストの外に置く。ループ内は早期 `continue` / `break`。
- **分岐の重複は型へ**。同じ条件の分岐が 2 箇所に現れたら、種類ごとのオブジェクトを辞書で引く形（ストラテジパターン）に移す。
- **種類は閉じた集合で表す**。結果や状態の種類はタグ付き union か列挙型で表し、1 箇所で網羅的に分岐する。想定外の種類に落ちる分岐には例外を置き、種類を足したときの漏れを必ず露見させる。言語やツールが網羅性を検査できるなら使う。
- **型の判定で分岐しない**。`instanceof` / `isinstance` のような型の判定で実装を見分けて特別扱いしない。その差はメンバにする。閉じた集合を 1 箇所で網羅的に分岐するのはこの限りではない。
- **条件の重複とネスト**。複数の条件を組み合わせる判定は、条件ひとつを 1 つの型にしたポリシーパターンで集約する。条件が 2〜3 個で 1 箇所なら、名前を付けた変数かメンバ関数で足りる。
- **フラグ引数**。呼び出し側が真偽値のリテラルを渡して処理を切り替える引数は、関数を分ける。状態の値としての真偽値（`isOverdrawn`）はフラグ引数ではない。

## コレクション

- **自前で実装する前に標準ライブラリ**。検索、絞り込み、変換、集約、グループ化、並べ替え、全件・いずれかの判定は、まず標準ライブラリの関数を探す。
- **ファーストクラスコレクション**。あるコレクションに対する同じ操作や不変条件が複数箇所に現れたら、そのコレクションを非公開で持つ型を作り、操作をメンバにする（期間内の取引履歴）。上の「型を与える基準」を満たすまでは素のコレクションのままでよい。
- 外へ渡すコレクションは複製するか不変にする。

## null・エラー・例外

- **「無い」を表す値（null / undefined / None）を返さない、渡さない、代入しない**が原則。「無い」がドメイン上の正当な状態のとき（任意項目が未入力）だけ許し、エラーや未初期化を「無い」で表さない。言語に「無い」の表現が複数あるなら 1 種類に統一する。
- 無いかもしれない値は既定値か早期 return で扱う。「あるはず」の決め打ち（非 null 断言）はせず、無ければ理由を添えて例外を投げる。
- 外から来た値（パースした JSON、CLI 引数、環境変数、HTTP のリクエストやレスポンス、フォームの入力）は受け取ったその場で検証して型を確定し、境界の外へ漏らさない。
- **戻り値の意図は型で表す**。`-1`、空文字、真偽値の成否で結果を表さない。
- **エラーは戻り値で返さず例外を投げる**。引数の不正、状態の不正、到達しないはずの分岐は、言語の標準の例外型で種類を区別して投げる。一方、利用者に見せる「正当な別結果」（値が欠測、データ未取得）はエラーではなくドメインの語彙なので、タグ付き union で返す。
- **例外を握り潰さない**。捕まえたら通知するか、文脈を足して投げ直すか、上の union に変換する。何もしない `catch` / `except` を書かない。

## そのほかの悪魔

- **デッドコード**は消す。履歴は git にある。
- **マジックナンバー**は名前付きの定数か、意味を持つ型のプロパティにする。
- **文字列型執着**。複数の値を区切り文字で 1 つの文字列に詰めない。種類を裸の文字列で表さず、列挙型か定数の集合で定義する。
- **メタプログラミング**。`eval` などの文字列からのコード実行と、属性名の文字列組み立てによるアクセスを書かない。
- **外部データはコンストラクタを通さずにオブジェクトを作る**。パースした外部データは入出力の境界に置く DTO に限り、ファクトリで検証してからドメインの型へ変換する。ドメインの型に生の外部データを渡さない。
- **サンプルコードのコピペ**。公式ドキュメントやライブラリのサンプルは API の説明であって設計の手本ではない。このファイルの形に直してから入れる。
- **銀の弾丸**。ここにある技法は問題があるときの対処であり、問題がない場所には適用しない。判断は ponytail と上の「型を与える基準」に従う。

## 名前設計

名前はクラス設計の入口。意味の広い名前にはロジックが寄ってきて神クラスになるので、**可能な限り具体的で、意味が狭い、目的に特化した名前**を選ぶ。`CONTEXT.md` の用語が第一候補で、そこにない概念は用語集に足してから使う。

- **存在駆動ではなく目的駆動**。「何であるか」（`Account` にすべてを詰める）ではなく「何のためにあるか」で分ける（一覧の 1 行、詳細画面に出す項目、グラフに描く残高の推移）。
- **文脈で意味が変わる名前は文脈ごとに型を分ける**。
- **形容詞で区別しているときはクラス化のチャンス**。`regularPrice` と `salePrice` が並んだら、その違いが型になる。
- **会話に出るのにコードに無い名前**を放置しない。仕様の会話で「締め日」「利用可能額」と言っているのに対応する型が無いなら、どこかに埋もれている。
- **仕様変更時の意味の変化**。意味が変わったら名前も変える。今の名前に引きずられて構造を決めない（アンカリング）。
- **技術駆動命名をしない**。`Manager`, `Processor`, `Handler`, `Util`, `Helper`, `Common`, `Info`, `Data` と、何も区別しない `Impl` を使わない。同じ役割の実装が複数あるときは区別点で名付ける（取引履歴の取得元なら `fileTransactions` と `apiTransactions`）。区別点が言えないのは実装が 1 つしかないからで、そのときは抽象のほうが要らない。
- **ロジック構造をなぞらない**。`isBalanceLessThanZero` ではなく、意図を表す `isOverdrawn`。
- **驚き最小**。名前が約束する以上のことをしない。getter と `is〜` は状態を変えない。実装が変わったら名前も変える。
- **連番命名**と、型名の繰り返し（`accountList`, `nameString`）をしない。
- **「動詞 + 目的語」の関数名は居場所を疑う**。目的語がそのクラスの関心事でないなら、目的語の側に型を作ってそこへ移し、**動詞 1 語で済む名前**にする。
- **Boolean 関数の居場所**。`is〜` / `has〜` / `can〜` は「このクラスが〜である」と読める型に置く。`Checker.isAccountOverdrawn(account)` ではなく `account.isOverdrawn`。

点検: 声に出して説明して意味が通るか。別の名前に置き換えるともっと狭くならないか。その名前のクラスに今の全メンバが自然に収まるか。

名前の表記（camelCase / snake_case など）はその言語の慣習に従う。上の例は表記の一例。

### 略語

名前は省略しない。変数・関数・クラスは辞書にある語か `CONTEXT.md` の用語で書き、`cnt`, `mgr`, `pos`, `idx`, `el`, `elem`, `btn`, `ctx`, `cfg` のような独自の省略を使わない。使ってよいのは次だけ。

- ループ添字の `i`, `j`、例外を受ける変数の `e`、本体が 1 行の無名関数の 1 文字引数。無名関数がネストするか 2 行以上になったら引数に名前を付ける
- 業界で標準の頭字語: `id`, `url`, `json`, `http`, `api`, `html`, `ui`
- `CONTEXT.md` に載せたドメインの略語（載せるまでは略さない）
- 単位は名前に含めず型で表す。`〜Meters` や `〜Px` の接尾辞を書いてよいのは、型を選べない入出力の境界（外部データのフィールド、外部 API の引数）と、同じ関数内に単位の違う数値が並ぶときだけ

## 関数設計

- **コマンドとクエリを分ける**。状態を変える関数は値を返さず、値を返す関数は状態を変えない。
- **引数は可能な限り少なく**。真偽値のリテラルと、同じ型が並ぶ引数は名前付き引数で渡す。
- **ベタ書きせず、目的ごとのまとまりで関数にする**。
- **型の明示**。公開する関数とクラスの公開メンバには、引数と戻り値の型を書く（型注釈、型ヒント、ドキュメントコメントなど言語の仕組みで）。

## コメント

- コメントは実装の劣化コピーになる。**処理をなぞるコメントは書かず**、**目的と、仕様変更時に壊れやすい点**を書く。
- **コメントで命名をごまかさない**。説明が要る名前は名前を直す。コメントに書いた制約（「0 以上」）は検証に移す。
- ドキュメントコメントは公開する型・関数と、名前と型から意図が読み切れない関数に書く。プロパティを名前どおりに言い直すだけのドキュメントコメントは書かない。
- 消したコードの残骸と、対応先のない `TODO` を残さない。

## モデリング

- **モデルはモノではなく目的達成の手段**。現実の「口座」を 1 クラスで写し取ろうとせず、目的別（一覧する、詳細を見せる、グラフに描く）にモデルを分ける。
- **モデルと実装は相互にフィードバックする**。実装で見つけた違和感は `CONTEXT.md` に戻す（`mattpocock-skills:domain-modeling`）。

## リファクタリングと指標

- **機能追加とリファクタリングを同じコミットに混ぜない**。スモールステップで、テストが緑の状態から緑の状態へ。
- テストの無いコードを直すときは、先に**仕様化テスト**で現在の振る舞いを固定する。あるべき形が見えないときは、捨てる前提の**試行リファクタリング**で構造を探ってから本番をやる。
- **動くコードを書いたら、設計し直してからコミット**。tdd の green の後の refactor がこれに当たる。
- 目安: 関数は実行行 10 行以内、クラスは 100 行以内、循環的複雑度 10 以下、一度に頭に置く概念は 4±1 個。超えたら関心が混ざっていないか上の各節で点検する。画面やテンプレートを宣言的に記述する関数は行数の目安から外し、代わりに中の業務判定がゼロであることを見る。

## 書式と識別子の言語

- 書式はその言語の標準的なスタイルに従い、リポジトリに整形ツールやリンターの設定があればそれに従う。
- ドメインのモジュールは入出力（ネットワーク、ファイル、画面）を参照せず、テストからそのまま呼べるようにする。
- テスト名は日本語の文（`unit-testing` スキル）。それ以外の識別子は英語。
