# 単体テストの規律

Khorikov『単体テストの考え方/使い方』の語彙（4 本の柱、観察可能な振る舞い、管理下 / 管理外の依存など）で書く。各規則の出典は人間向けに `SOURCES.md` にあり、作業時に読む必要はない。規則は言語とテストフレームワークを問わない。

`mattpocock-skills:tdd` が red→green のループ、seam、アンチパターン（実装結合・トートロジー・水平スライス）を担い、`code-design` がクラスと関数の設計を担い、`ponytail:ponytail` が最小のコードを担う。このスキルは**残す価値のあるテストの条件**と**そのためのコードの分け方**を決める。

**規約の正はこのファイルであり、既存のテストではない**。既存のテストがここに反していたら手本にせず、触る機会に直す。

## 4 本の柱

良いテストは次の 4 つで採点する。

1. **退行（regression）に対する保護**: バグを見つける力。実行されるコードの量・複雑さ・ドメイン上の重要性に比例する。
2. **リファクタリングへの耐性**: 振る舞いが変わっていないのに赤くなる偽陽性を出さない力。
3. **迅速なフィードバック**
4. **保守のしやすさ**

リファクタリングへの耐性と保守のしやすさは**妥協しない**。偽陽性を出すテストは、退行保護がどれだけ高くても削除する。退行保護と迅速なフィードバックは両立しないので、テストの層で配分する。

| 層 | 対象 | 配分 |
|---|---|---|
| 単体テスト | 関数的核（ドメインの型と計算） | 多数。迅速さを取る |
| 統合テスト | コントローラを、管理下の依存は本物、管理外の依存はテストダブルにして通す | 少数。主要な道筋 1 本と、単体テストで覆えない端のケース |
| 手動確認 | 画面の見た目など自動化に見合わないもの | 主要な導線だけ |

テストフレームワークはプロジェクトが使っているものに従い、モックライブラリやテスト用の差し替え機構（モンキーパッチ、モジュールのモック）は使わない。依存は明示的に注入する。

## 何をテストするか

- テストの単位は**振る舞いの単位**であり、クラスや関数という**コードの単位ではない**。1 つのテストは「利用者がこのコードに何をさせたいか」を 1 文で言えるものに対応する。隔離するのはテスト同士であって、クラス同士ではない（古典学派）。
- 検証するのは**観察可能な振る舞い**だけで、実装の詳細は検証しない。非公開の関数と内部状態は公開 API 経由で間接的に検証される。
- コードを「複雑さ・ドメイン上の重要性」と「協力者の数」の 2 軸で 4 種類に分ける。

  | 種類 | 扱い |
  |---|---|
  | **ドメインモデル / アルゴリズム**（複雑、協力者が少ない） | 単体テストで厚く守る。費用対効果が最も高い |
  | **取るに足らないコード**（getter、委譲だけの関数） | テストしない |
  | **コントローラ**（単純、協力者が多い） | 統合テストか手動確認で薄く守る |
  | **過度に複雑なコード**（複雑、かつ協力者も多い） | テストする前に、上の 2 つへ分割する |

- カバレッジ率は**否定の指標**としてだけ使う。低ければ問題、高くても良い証拠にはならない。

## 関数的核と質素なコントローラ

コードを 2 種類に分ける。

- **関数的核 (functional core)**: 入力から出力を計算するだけの部分。ネットワークもファイルも画面も持たない。ここに複雑さを集め、**出力値ベースのテスト**（入力を与え、戻り値を検証）で守る。
- **質素なコントローラ (humble object)**: 入出力とオーケストレーションだけを行う薄い層。決定は核に頼み、自分は決定しない。

「過度に複雑なコード」を見つけたら、決定（何をすべきか）を核に、実行（それを行う）をコントローラに分けてからテストを書く。エントリポイントが太るのはこの分割ができていない兆候である。

よくあるコードの対応:

| コード | 分類 | テスト |
|---|---|---|
| ドメインの型と計算: 値の変換と判定、時系列の集計、前回値との比較（上昇・変化なし・下降）、表示用の文字列（単位付き数値、日時）の整形 | 関数的核 | 出力値ベース。入出力のオブジェクト（ファイルハンドル、HTTP のレスポンス、画面の要素）を引数に取らせない。取っていたら核になっていない |
| 外部データ（JSON、CSV、API のレスポンス）の DTO からドメインの型への変換と検証 | 関数的核 | 出力値ベース。正常な形と、壊れた形で例外になることを確かめる |
| 出力用の文字列やデータ構造（HTML、SVG、レポート）を組み立てて返すだけの関数 | 関数的核 | 出力値ベース。ただし検証するのは値や構造であって、文字列全体の一致ではない。文字列全体を固定すると装飾の変更で赤くなる |
| 画面・ファイル・標準出力へ書き出す関数、エントリポイント | 質素なコントローラ | 計算済みの値を受けて出力するだけにして単体テストの対象から外す（`code-design` のスマート UI） |
| 外部 API や他者のサービスから読む関数 | **管理外のプロセス外依存** | 取得関数を引数で受け取れるようにし、テストでは固定のデータを返す関数を渡す。読み取り専用なので要るのはスタブで、呼び出しの検証は要らない |
| このアプリだけが読み書きするファイルやデータベース、同梱のデータファイル | 管理下のプロセス外依存 | テストダブルにせず本物を使う（一時ディレクトリ、テスト用のデータベース）。同梱データは変換関数のテストで実ファイルを 1 つ読んで通し、形式が壊れたら気づくようにする |

## テストダブル

- **モックとスタブを区別する**。モックは外へ出ていくコマンドの検証、スタブは中へ入ってくるデータの供給。**スタブとのやりとりは決して検証しない**。「スタブが 1 回呼ばれたか」は実装の詳細の検証であり、偽陽性の元。
- モックで検証してよいのは、**管理外のプロセス外依存**（他者からも観測される外部システム: メール送信、外部 API への書き込み、メッセージの発行）へ出ていくコマンドだけ。それ以外で**呼び出し回数や引数を検証したくなったら設計を疑う**。
- 自分のクラス・内部の協力者は**モックしない**。seam を満たす in-memory の Fake（固定のデータを返す関数、配列を返す関数）は可。Fake はテストコードの側に置き、本番コードに置かない。
- **自分が所有する型だけをテストダブルにする**。HTTP クライアントや外部 SDK を直接差し替えず、それを包む自前の取得関数を差し替える。
- **抽象は差し替える必要が実際にあるときだけ作る**。実装が 1 つしかなく、テストでも本物を使える依存に間接層を被せない。seam が正当なのは、テストから動かせないもの（画面、実機）と管理外の依存である。seam は利用側の目的の単位で切る。
- 検証方式の優先順位: **出力値ベース > 状態ベース > コミュニケーションベース**。

## 時間

- **現在時刻は明示的な依存として注入する**。本番コードで現在時刻を直接取得せず、引数で受け取る。テストでは固定の日時を渡す。乱数も同じ。
- 定期実行や待機（タイマー、スリープ）はコントローラに置き、テストしない。

## テストの形

- **AAA**（準備・実行・確認）を空行で 3 節に区切る。節の見出しコメントは、節が長くて境目が読み取れないときだけ。実行は 1 行。確認は 1 つの振る舞いに対する複数 assert なら可。テストの中に `if` やループを書かない（入力違いのケースを並べるのは下記のパラメータ化で）。
- フィクスチャは **非公開のファクトリ関数**で作り、既定引数で「このテストに関係する値だけ」を呼び出し側に書かせる。テストファイルのトップレベルに可変状態を置かない。

  ```
  account(balance = 1000, overdraftLimit = 0) -> Account(balance, overdraftLimit, ...)
  ```

- **命名は日本語の文**。振る舞いを非プログラマにも伝わる形で述べ、テスト対象の関数名とクラス名を含めない。

  - `残高が 0 のとき残高バーの高さは 0 になる`
  - `前回より残高が多ければ上昇の矢印になる`

  テスト名に日本語を書けない言語やフレームワークでは、説明文の引数や表示名の機能に日本語の文を書く。

- 同じ振る舞いを入力違いで確かめるときは、フレームワークのパラメータ化の機能（無ければケースの配列からテストを生成する）を使う。別の振る舞いを 1 つにまとめない。
- 期待値は**仕様から来るリテラル**で書く。本番コードと同じ計算で期待値を作らない（ドメイン知識の漏洩、tdd スキルのトートロジー規則）。
- **テストのためだけの本番コードを書かない**（コードの汚染）。テスト用のフラグ、テストのための公開、内部状態の公開をしない。必要に感じたら、観察可能な振る舞いを通せていないか、取り出すべき型が埋もれている。
- 戻り値をプレーンな値として設計し、構造の等価比較 1 つで確認が済むようにする。

## ワークフロー

1. `mattpocock-skills:tdd` スキルを読み、ループの規則に従う。
2. 最初のテストを書く前に、対象コードを上の 4 種類に分類し、seam を書き出す。「過度に複雑」なら先に分割する。
3. 1 スライスずつ red → green → refactor。
4. 完了時に各テストを 4 本の柱で見直す。リファクタリングへの耐性を欠くテストは削除する。
