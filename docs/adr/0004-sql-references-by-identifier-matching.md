# ADR-0004: 表・列は接続中の DB の辞書から、SQL が使う表・列は識別子の照合で決める

日付: 2026-11-01 / 状態: 採用

## 文脈

Phase 4 で「このカラムを変えたら、どの SQL・どの画面に響くか」に答える。必要なのは (1) 表・列のノード、(2) MyBatis の SQL 文のノード、(3) SQL 文 → 表・列の辺。
IDEAS.md の当初案は「SQL は SQL パーサで」だった。最初の解析対象はこのリポジトリ自身（Oracle に接続できる）。

## 決定

1. **表と列は接続中の Oracle の `USER_TAB_COLUMNS` から読む**（`SchemaMapper` → `DatabaseSchema`）。ノード名は `表`（TABLE）と `表.列`（COLUMN）で、辞書どおり大文字
2. **MyBatis マッパー XML の `select / insert / update / delete` を `namespace#id` の METHOD ノードにする**（`MyBatisMapperAnalysis`）。Java 解析が作る Mapper インターフェースのメソッドと同じ名前になるので、同じノードに合流し、Controller → Mapper メソッド → 列 と一本に繋がる
3. **SQL がどの表・列を使うかは SQL パーサではなく識別子の照合で決める**（`DatabaseSchema.dependenciesOf`）
   - SQL 文の中の識別子を取り出し（`#{}` / `${}` は先に除く）、スキーマの表名と一致すれば確実な辺（1.0）
   - 列名は、それを持つ表が参照表の中に 1 つなら確実な辺、複数ならそれぞれへのあいまいな辺（0.5。Phase 5 で Jev が付け直す）
   - 参照していない表の列名は辺にしない
4. マッパー XML の場所は `hamon.analysis.mapper-roots`（既定 `src/main/resources`）。ルート要素が `mapper` でない XML は読み飛ばす。DOCTYPE の外部 DTD と外部実体は取りに行かない

## 理由

- 辞書ビューは 1 文で済み、DDL を読むより実際の表と一致する。対象システムの DB に繋げるのは SI の影響調査では普通の前提
- SQL パーサ（JSqlParser など）は `#{}` のバインド変数、`<if>` などの動的 SQL、Oracle 方言（`WITH … CYCLE`）で失敗しやすく、失敗したときの受け皿として結局は識別子照合が要る。識別子照合だけなら動的 SQL でも壊れない
- 照合で断定できない部分を「あいまいな辺」として残すのは、Java 解析の同名メソッドへの辺と同じ扱いで、hamon の設計（静的解析は漏れなく候補を出し、Jev が確からしさを付ける）に合う
- 列名が表の列名と一致するだけで辺になるので漏れは少ない。余計な辺は確からしさで区別する

## 影響

- 引用符付き識別子、`${}` で組み立てる表名、`<include refid>` の展開、`SELECT *` の列展開は扱わない（コード中の `shortcut:` コメント）。対象システムで問題になったら SQL パーサに切り替える。seam は `DatabaseSchema.dependenciesOf`
- 列名と同じ単語が別の意味で SQL に現れる（結果列の別名など）と、確からしさ 1 の余計な辺になる
- 列は表に依存する辺を張っていない。表を変更点にしたときの影響は、その表を直接使う SQL 文から辿る
- 他リポジトリを解析するときは、そのシステムの DB（またはスキーマを複製した DB）に接続する必要がある
